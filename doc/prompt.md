# Codex 开发任务：从零构建 Android 本地视频管理与播放器

你是一名资深 Android 工程师、架构师和测试工程师。请从零开发一款高质量的 Android 本地视频管理与播放应用。

不要只给出方案或示例代码。你需要在当前工作区内完成需求分析、技术设计、项目搭建、功能实现、自动化测试和 APK 构建，并持续修复编译错误与测试失败。

## 一、项目目标

开发一款完全离线运行的 Android 本地视频播放器，核心定位是：

**扫描手机视频 + 按文件夹浏览 + 每个视频独立播放次数统计 + 每个视频独立断点续播 + 倍速播放。**

应用不依赖服务器、账号体系、云服务或网络 API。视频文件、播放历史、播放次数和断点记录均保存在本地。

优先保证功能正确性、数据可靠性和使用体验，而不是一开始追求复杂功能。

## 二、技术栈与工程约束

采用以下技术方案：

- 开发语言：Kotlin。
- UI：Jetpack Compose + Material 3。
- 视频播放：AndroidX Media3 ExoPlayer。
- 本地数据库：Room + SQLite。
- 异步任务：Kotlin Coroutines + Flow。
- 依赖注入：优先使用构造器注入，必要时采用轻量方案，不要为简单项目引入过多框架。
- 项目构建：Gradle + Kotlin DSL。
- 架构：分层架构，UI、业务逻辑、数据访问和播放控制职责清晰。
- 测试：JUnit、AndroidX Test、Room 测试，以及必要的播放器和扫描逻辑测试。

具体要求：

1. 使用当前稳定且相互兼容的 Android SDK、Android Gradle Plugin、Kotlin、Compose 和 Media3 版本，并在项目中固定版本。
2. 不要使用未经验证的 API、虚构依赖或过时的 Android 存储访问方案。
3. 合理设置 minSdk 和 targetSdk，优先覆盖常见 Android 手机。
4. 兼容 Android 13 及以上的媒体权限机制，以及较早 Android 版本的对应权限机制。
5. 针对华为等 Android 兼容设备进行适配设计，但不得假定所有 HarmonyOS 版本都能运行标准 Android APK；在真实设备验证前，不得宣称兼容性已得到保证。
6. 默认不接入广告、统计 SDK、云端服务或任何非必要的第三方服务。
7. 应用不修改、不移动、不删除用户的原始视频文件。

## 三、核心功能需求

### 1. 首次启动与媒体扫描

应用启动后，引导用户授权访问本地视频，并扫描设备中可访问的视频文件。

要求：

- 使用 MediaStore 获取系统已索引的视频。
- 展示扫描进度、已发现的视频数量和必要的错误信息。
- 支持首次全量扫描、手动重新扫描和后续增量更新。
- 对新增、删除、重命名、移动的视频进行合理处理。
- 通过 MediaStore 变化通知或其他适当机制刷新索引；不要每次进入页面都执行低效的全盘扫描。
- 扫描过程不能阻塞主线程。
- 扫描失败、权限被撤销、设备存储不可用时，应用不能崩溃。
- 重复扫描不能生成重复视频记录。
- 不要因为一次扫描未完成、权限暂时不可用或某个文件读取失败，就直接删除整个数据库中已有的记录。

Android 存储访问要求：

- 优先使用 MediaStore 访问系统媒体库。
- 使用适当的权限请求方式，并说明不同 Android 版本的权限差异。
- 对系统媒体库无法覆盖的特殊目录，可以评估通过 Storage Access Framework 让用户主动选择文件夹的方案。
- 如果支持 SAF 文件夹授权，需要妥善保存授权状态，并在授权失效时给出提示。
- 不要默认申请不必要的 MANAGE_EXTERNAL_STORAGE 权限。
- 明确区分文件不可访问、文件已删除、权限丢失和扫描尚未完成等状态。

### 2. 按真实文件夹组织视频

这是核心功能，必须实现。

首页展示手机中可访问的视频文件夹，而不是只展示一个扁平的视频列表。

示例：

视频库
- Movies/
  - movie-a.mp4
  - movie-b.mkv
- DCIM/
  - Camera/
    - video-001.mp4
- Download/
  - tutorial.mp4
- 自定义目录/
  - video-002.mp4

要求：

- 按真实目录路径归类，保留文件夹层级。
- 支持进入文件夹、返回上级目录。
- 文件夹展示视频数量。
- 文件夹内的视频展示文件名、时长、文件大小、分辨率（可获取时）和上次播放状态。
- 支持按名称、修改时间、大小和时长排序。
- 支持视频名称搜索。
- 空文件夹和没有视频的目录不必默认展示。
- 不同目录中同名视频必须能够区分。
- 对无法获取真实路径的内容 URI，使用可用的目录元数据或授权目录结构组织，不能伪造路径。
- 目录移动、文件重命名和文件删除后，正确更新索引，同时尽可能保留能够可靠匹配的历史记录。

### 3. 每个视频独立保存播放断点

这是最高优先级的功能之一。

**每一个视频都必须拥有独立的播放进度记录，不能只保存最近播放视频的进度。**

例如：

- A.mp4 上次播放到 00:12:30。
- B.mp4 上次播放到 00:45:10。
- C.mp4 上次播放到 00:03:20。

分别重新打开 A、B、C 时，必须恢复各自对应的播放位置。

要求：

1. 视频进度按视频唯一标识保存。
2. 播放进度必须持久化到 Room，而不是只保存在内存中。
3. 进入播放器后，正确读取该视频的历史进度。
4. 对首次播放的视频，从头开始。
5. 对有历史进度的视频，默认恢复上次有效位置，并允许用户手动拖动。
6. 在播放过程中定期保存进度，但不能过于频繁地写数据库。
7. 在暂停、切换视频、正常退出播放器、播放结束和生命周期变化等关键时机保存进度。
8. 即使应用进程被系统杀死，已经持久化的进度也应能恢复。
9. 不允许因为切换视频、返回列表、旋转屏幕或重建播放器而覆盖其他视频的断点。
10. 视频播放结束后，应根据明确的产品规则处理断点：默认将该视频标记为已看完，下次播放从头开始；不能错误地恢复到视频末尾。
11. 对短视频、直播流、时长未知的媒体和不可 seek 的媒体进行合理处理。
12. 对无效进度、超出时长的进度和媒体时长变化进行校验。
13. 如果视频文件被移动或重命名，在可以可靠识别文件身份时尽可能保留播放历史；如果无法确认身份，不得错误地把另一视频的进度套用过来。

请设计独立的 PlaybackProgressRepository，并定义进度保存和恢复策略。

需要特别测试：快速连续切换 A、B、C 三个视频时，不会发生异步写入乱序导致进度串号。

### 4. 每个视频独立统计播放次数

所有视频都要有独立的播放次数统计。

示例：

| 视频 | 播放次数 | 上次播放位置 |
|---|---:|---|
| A.mp4 | 12 | 00:12:30 |
| B.mp4 | 3 | 00:45:10 |
| C.mp4 | 1 | 00:03:20 |

要求：

- 播放次数保存在 Room 中。
- 播放次数与具体视频关联，而不是保存全局计数。
- 每个视频列表项展示播放次数。
- 视频详情可以查看播放次数、上次播放时间、上次播放位置和播放完成状态。
- 数据库升级或应用重启不能造成播放次数丢失或重复累计。
- 暂停、恢复、拖动进度、切换倍速不能单独触发计数。
- 同一次播放会话不能因为播放器重建、Activity 重建或页面切换而重复计数。

请明确并实现播放次数的计数规则：

- 视频进入实际播放状态后开始观察播放会话。
- 默认以一次有效播放会话累计一次播放次数。
- 为避免误触，可设置最小有效播放条件，例如累计实际播放 10 秒，或者对于较短的视频播放达到合理比例。
- 对用户主动退出、播放失败、重复打开和已看完视频重新播放等情况，制定一致的计数规则。
- 将计数状态与播放器生命周期解耦，避免进程重建造成重复累计。
- 如果采用延迟确认计数，必须明确何时落库，以及应用被杀死时如何避免丢失或重复。

请将播放次数规则封装在独立业务组件中，避免散落在 UI 代码里。

### 5. 倍速播放

必须支持常用播放倍速：

- 0.5x
- 0.75x
- 1.0x
- 1.25x
- 1.5x
- 1.75x
- 2.0x
- 2.5x
- 3.0x

要求：

- 使用 Media3 的播放参数控制播放速度。
- 播放器提供直观的倍速选择入口。
- 显示当前倍速。
- 切换倍速不重置播放位置。
- 倍速变化不影响播放次数统计。
- 根据媒体能力和系统支持情况合理处理异常倍速。
- 默认速度为 1.0x。
- 可以考虑记住用户上次选择的倍速，但不要默认让某个视频永久锁定不同倍速，除非后续产品设计明确需要。

### 6. 播放器界面

实现完整、可用的本地视频播放器界面。

至少包括：

- 播放和暂停。
- 当前播放时间、总时长。
- 进度条与拖动 seek。
- 快退、快进。
- 当前倍速及倍速选择。
- 视频名称。
- 退出播放器。
- 恢复历史断点的提示或明确的恢复行为。
- 播放错误提示。
- 加载状态。
- 横竖屏适配。
- 合理的沉浸式播放体验。
- 屏幕旋转时尽量保留播放状态，避免重复累计播放次数。
- 退出播放器时返回原文件夹，而不是无条件返回首页。

不要只实现播放器外观，所有控件都必须具有实际功能。

### 7. 视频列表与观看状态

每个视频至少保存以下信息：

- 唯一标识。
- 视频名称。
- 可访问的 URI。
- 可获取的目录路径或目录标识。
- 文件大小。
- 时长。
- 修改时间。
- 最近一次播放位置。
- 播放次数。
- 最近播放时间。

视频列表提供以下展示能力：

- 从未播放。
- 正在观看。
- 已看完。
- 播放次数。
- 上次播放位置。

支持按名称、最近播放时间、播放次数排序。

对于“正在观看”和“已看完”的判断，需要明确统一的规则，避免不同页面出现不一致结果。

### 8. 本地设置

提供简单的设置页面，至少包括：

## 四、数据模型设计

使用 Room 持久化数据。

至少设计以下数据实体：

### VideoEntity

保存视频索引和媒体元数据。

字段示例：

- id
- mediaStoreId 或其他稳定标识
- contentUri
- volumeName
- relativePath 或可用目录标识
- displayName
- sizeBytes
- durationMs
- width
- height
- dateModified
- lastScannedAt
- availabilityStatus

### PlaybackRecordEntity

保存每个视频的播放统计和状态。

字段示例：

- videoId
- positionMs
- playCount
- lastPlayedAt
- completionStatus
- lastPlaybackSpeed（可选）
- updatedAt

### PlaybackSessionEntity（如有必要）

如果播放次数采用延迟确认、会话去重或崩溃恢复机制，可设计独立会话表。

必须遵守：

- 视频索引和播放记录的生命周期应合理解耦。
- 删除媒体文件不应导致整个数据库损坏。
- 数据库关联和索引应符合实际查询需求。
- 断点和播放次数更新应具备事务一致性。
- 数据库升级必须有迁移策略。
- 所有字段、主键、唯一约束和索引都需要给出设计理由。

请根据实际情况调整上述字段，而不是机械照抄。

## 六、关键边界场景

实现时必须主动考虑以下情况：

1. 首次启动没有视频。
2. 用户拒绝媒体权限。
3. 用户授予权限后又撤销。
4. 手机中存在大量视频文件。
5. 同名视频位于不同目录。
6. 视频被移动、重命名或删除。
7. 文件 URI 失效。
8. 视频播放中应用进程被杀死。
9. 用户连续切换多个视频。
10. 用户快速暂停、恢复和拖动进度条。
11. 播放器因旋转屏幕而重建。
12. 视频播放结束后再次打开。
13. 播放器初始化失败或格式不支持。
14. 文件访问权限不足。
15. 数据库更新期间应用退出。
16. 重复扫描同一批文件。
17. 媒体库中存在损坏文件或异常元数据。
18. 手机存储空间不足。
19. 数据库中存在旧版本留下的无效记录。
20. 设备重启后重新打开应用。

不能只处理理想路径。

## 八、测试要求

必须编写自动化测试，重点覆盖以下行为。

### 断点隔离测试

- A、B、C 三个视频分别保存不同进度。
- 分别重新打开三个视频，验证恢复位置正确。
- 连续切换视频，验证不会串号。
- 模拟播放器重建，验证不会重复覆盖断点。
- 模拟进程终止后重新启动，验证数据库中的断点仍然有效。
- 视频播放结束后，验证再次打开时按约定从头播放。

### 播放次数测试

- 一个有效播放会话只计数一次。
- 暂停和恢复不会重复计数。
- 拖动进度不会重复计数。
- 改变倍速不会重复计数。
- Activity 重建不会重复计数。
- 不同视频的播放次数互不影响。
- 数据库持久化和重启后统计正确。
- 播放失败和无效播放会话不应错误累计。

### 扫描测试

- 同一目录重复扫描不产生重复数据。
- 新增文件能正确入库。
- 删除文件能更新可用状态。
- 同名文件能正确区分。
- 部分扫描失败不会清空有效数据。
- 权限撤销时不会崩溃。
- 文件夹归类符合目录结构。

### 播放器测试

- 播放、暂停、seek 正常。
- 倍速切换正常。
- 播放位置不会因倍速切换而重置。
- 视频结束状态正确。
- 播放错误有合理反馈。

优先实现可自动化的单元测试和数据库测试。涉及 Android 实际媒体权限、文件系统和解码器的行为，应补充设备测试步骤，不要用纯 Mock 测试冒充真实设备验证。

## 十、执行规则

1. 直接在当前工作区执行任务，不要只回复一份教程。
2. 先阅读工作区现状，再创建或修改文件。
3. 不要一次生成所有代码后就结束，应按阶段实施和验证。
4. 每完成一个阶段，更新 docs/implementation-plan.md 中的进度。
5. 发现设计缺陷时，先修正文档，再修改实现。
6. 每次重要修改后执行相关测试或构建。
7. 编译失败时分析根因并修复，不要通过删除测试、关闭检查或随意降低 SDK 要求掩盖问题。
8. 遇到不确定的 Android API 行为，优先查阅官方文档和当前依赖版本的 API，而不是猜测。
9. 不要把 TODO、占位页面、假数据或未接通的按钮视为功能完成。
10. 不要在没有真实设备验证的情况下宣称所有手机都兼容。
11. 对不影响核心功能的非关键决策自行采用合理默认值，不要频繁中断开发向用户提问。
12. 不要擅自添加云同步、账号系统、广告、社交功能或与本项目无关的功能。

## 十一、最终验收标准

只有同时满足以下条件，才能认为 MVP 完成：

- 应用能够扫描并展示可访问的本地视频。
- 视频按照真实目录结构组织。
- 每个视频可以独立打开和播放。
- 每个视频拥有独立的播放断点。
- 多个视频之间切换不会造成进度串号。
- 应用退出或进程被杀死后，已保存的断点能够恢复。
- 每个视频具有独立且持久化的播放次数。
- 同一次播放会话不会因为播放器重建而重复累计。
- 播放器支持常用倍速。
- 播放结束后行为符合约定。
- 权限异常、文件失效和扫描失败不会导致应用崩溃或清空全部有效记录。
- 核心自动化测试通过。
- APK 构建成功，或明确记录阻碍构建的实际环境问题。
